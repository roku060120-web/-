## 00. 前提と制約

| 項目 | 内容 |
|---|---|
| データの機微度 | 成績・単位・収支・人物の連絡先。**認証なしでの外部流出は絶対不可**（v2.1でログイン経由のプライベート同期のみ許可） |
| 元データの所在 | Google ドライブ（本人アカウント） |
| 完成形 | このPCでアイコン／ショートカットをクリック → アプリが起動し、普段使いできる |
| 公開の禁止 | **誰でも読める**形でのオンライン掲載（Artifact等）、GitHubの公開リポジトリへの個人データ配置。認証必須・本人専用のクラウド保存（Supabase, RLSで他人からは不可視）はv2.1で許可 |

**GitHubリポジトリは現在 public。** 個人データを1バイトも置かないのは当然として、
非公開化するまで新しいコミットはpushしない。`.gitignore` には
`data/` `*.pdf` `*.csv` `*.json`(状態ファイル) `.env` 等を追加済み。

## 01. 決定したこと

| 領域 | 決定 |
|---|---|
| データの正 | **PCのローカルファイル**（アプリが読み書きするマスター） |
| Google の役割 | 入力の供給源に降格。**片方向**でPCに流し込むだけ |
| 公開エンドポイント | **作らない**（v1 の doGet/doPost 案は破棄） |
| スケジュール | Googleカレンダー併用（読み取りのみ） |
| 睡眠 | iPhone ショートカット → Drive → PC |
| 単位 | 作戦マップ（スキルツリー）＋充足サマリーバー |

## 02. アーキテクチャ（v2）

```
        ┌──────────── Google の中だけで完結 ────────────┐
        │                                               │
  成績表PDF ─┐                                          │
  カレンダー ─┼─▶ GAS（時間トリガー）                    │
  Gmail速報 ─┤      └─▶ スプレッドシートを更新           │
  iOSショートカット(睡眠) ─┘      └─▶ lifegame-feed.json を Drive に書き出す
        │                                               │
        └───────────────────┬───────────────────────────┘
                            │ Google ドライブ デスクトップ版が同期
                            ▼
                  PC のローカルフォルダ
                            │ 読み込み（片方向）
                            ▼
        ┌─── ライフゲーム（ローカルサーバ + ブラウザ）───┐
        │  data/state.json  ← 唯一の正（アプリが読み書き）│
        └───────────────────────────────────────────────┘
```

**要点**

- インターネットに公開されるURLが**ひとつも存在しない**。v1 で懸念だった
  「成績と収支が乗った公開エンドポイント」が消える
- Googleに触れるのはGAS（自分のアカウント内で動く）だけ。PCは同期されたファイルを読むだけ
- アプリの書き込み（タスク・所持金・手入力）は**ローカルの `data/state.json` に閉じる**。
  Googleには送り返さない
- **片方向なので同期の競合が起きない**。v1 の双方向案にあった一番厄介な問題が消える
- ネットが切れていても普段使いできる

**技術的な注意**：Google ドライブ デスクトップ版では、Googleネイティブ形式のスプレッドシートは
`.gsheet`（中身のないショートカット）としてしか同期されない。
そのため **GAS が通常ファイルとして `lifegame-feed.json` を書き出す**必要がある。
ここがこの構成の肝。

## 03. 起動方法（完成形）

`file://` で開くとローカルJSONを `fetch` できない（ブラウザの制限）ため、極小のローカルサーバを噛ませる。

| 案 | 内容 | 評価 |
|---|---|---|
| **A. ランチャースクリプト** | Mac: `LifeGame.command` / Win: `LifeGame.bat` をダブルクリック → サーバ起動＋ブラウザを開く | **採用**。実装が軽く確実 |
| B. PWAとして追加 | Chromeの「アプリとしてインストール」でDock/タスクバーに常駐。独立ウィンドウでアプリらしくなる | Aの上に被せる |
| C. ログイン時に自動起動 | サーバを常駐させ、アイコンは開くだけにする | 普段使いするなら最終的にこれ |
| D. Tauri / Electron | 完全なネイティブアプリ | ビルド環境が要る。将来 |

**A → B → C** の順に育てる。Cまで行けば「クリックすると開く常駐アプリ」になる。

## 04. データモデル

ローカル `data/state.json`（アプリが読み書きする正）と、
Drive から流れてくる `lifegame-feed.json`（読み取り専用）の2本立て。

### feed（Google → PC、読み取り専用）

| セクション | 中身 | 更新頻度 |
|---|---|---|
| `credits` | 履修台帳（科目・単位・評価・区分・カテゴリ） | 学期ごと |
| `requirements` | 卒業要件（要件ID・必要単位・算入上限・マッチ条件・適用年度） | 改定時のみ |
| `courses` | 履修候補（開講学期・曜限・単位・対象要件） | 履修登録前 |
| `calendar` | 単発予定（試験・シフト・用事） | 1時間ごと |
| `sleep` | 睡眠ログ（日付・就寝・起床・時間） | 毎朝 |
| `money` | 収支ログ（速報メール由来） | 5分ごと |

### state（PC内、アプリが書き込む正）

タスク、時間割テンプレート、人物、残高アンカー、手入力の記録、要件割り当ての手動上書き。

**単位は足し算ではない**：1科目が複数要件に算入されたり算入上限があるため、
「科目をどのバケツに割り当てるか」の最適化問題になる。
実装は**貪欲法（上限の厳しい要件から充当）＋画面上の手動オーバーライド**。

## 05. 画面仕様

### CREDITS — 作戦マップ
- 卒業を頂点、要件を中間、科目を葉とするツリー。ノードの大きさ＝単位数
- 状態4種：取得済み(緑) / 履修中(アンバー・破線) / 履修可能(緑の輪郭) / 未取得(暗い)
- 一覧性はツリーの弱点なので、**上端の1本のサマリーバー**が全体充足率を受け持つ
- NETWORK画面との差別化は**レイアウトの性質**で行う。人物図は力学レイアウトで毎回形が変わるが、
  作戦マップは決定論的な階層レイアウトで常に同じ形。地図として記憶できることに意味がある
- ノードをタップ → その要件を埋めた科目、残り単位、使える候補科目

### OPS — 3層に分ける

| 層 | スパン | 住所 |
|---|---|---|
| 要件 | 数年 | CREDITS画面（OPSには出さない） |
| 履修登録 | 学期 | 締切付きタスクとしてOPSに出す |
| 課題・レポート | 日〜週 | 既存のタスクの仕組み |

### SCHEDULE — 2層合成＋カレンダー
- 時間割マスター＋予定例外の2層（`juku-schedule` が既に到達している形を流用）
- 時間割テンプレートはローカル、単発予定は feed から。**カレンダーへの書き込みはしない**
- 上部に「次の予定までのカウントダウン」と「今日の残り」。タスク締切をピンとして重ねる

### HEALTH — 睡眠を他の画面に効かせる
- 平均睡眠＋当日の予定密度から「今日の可処分エネルギー」を算出
- 必須タスクの合計がエネルギーを超えたら「作戦過負荷」警告
- 表示で終わらせないことで、記録を続ける動機が設計に組み込まれる

## 08. 成績表の形式（実データ確認済み・2026-08-18）

大学の成績表システムが出力するPDFは、テキスト抽出が素直に効き、
**分野コードによる階層構造**を持っていることを確認した。パーサーは正規表現で足りる。

```
分野：30-17-21 専門教育科目 ○○専攻 選択必修（３類） 取得合計 4.0単位
  科目名称 / 担当者 / 評語 / 単位 / 追試再試 / 年度 / 開講学期 / 取得学年
```

- **分野コード（`NN-NN-NN`）が卒業要件のバケツIDそのもの**。要件シートのマッチ条件は
  コードのプレフィックス（例 `30-17-*`）で書けるため、科目名の表記ゆれに依存しない
- 各分野ブロックに「取得合計 X.X単位」が入っている。**パーサーの検算に使える**
- 評語：`S A B C P` = 合格 / `D F` = **不合格** / `G` = 認定 / `？` = 未確定（履修中）/ `－` = 評語なし
- 同一科目名で担当者違いの行が並ぶことがある（クラス分け）。科目名だけでは一意にならない

### 状態は4つでは足りない（設計の修正）

実データを見て判明。**不合格（D/F）の科目は「取得合計」に算入されない**ため、
「履修したが単位にならなかった科目」が存在する。これを表示しないと作戦マップが実態とズレる。

| 状態 | 表示 |
|---|---|
| 取得済み | 緑・塗り |
| 履修中（`？`） | アンバー・破線 |
| 履修可能 | 緑の輪郭 |
| **不合格（再履修候補）** | **赤・打ち消し** ← 追加 |
| 未取得 | 暗い輪郭 |

## 09. バイトのシフトは既存シートから取れる

Drive の `時間割マスター`（`juku-schedule` プロジェクトが使っているシート）に、
**自分が講師として担当するコマが曜日・時間つきで入っている**。
`講師 = 自分` の行を抽出すれば、バイトのシフトが週次スケジュールに自動で載る。
ライフゲームと juku-schedule はここで自然に繋がる。

一方、**大学の時間割は Drive に見当たらない**ため、別途用意が必要。

## 11. ログイン・クラウド同期（P1.6, 2026-08-25）

**要件**：スマホなど他端末からもログインして続きを見たい。成績・収支・連絡先などの
機微データも、**自分だけがアクセスできるプライベートな形**であればクラウドに置いてよい。

**構成**：Supabaseプロジェクト `life-game`（組織 `hddojmndvzdgpjvnlffz`, リージョン
`ap-northeast-1`, 無料プラン）を新規作成。

| 項目 | 内容 |
|---|---|
| 認証 | メールのマジックリンク（パスワード不要） |
| テーブル | `public.app_state`（`user_id uuid primary key references auth.users`, `data jsonb`, `updated_at`） |
| アクセス制御 | RLSで `auth.uid() = user_id` の行しか select/insert/update/delete できない。他人からは不可視 |
| クライアント | `@supabase/supabase-js` のUMDビルドを `js/vendor/supabase.js` にベンダリング（CDN依存なし） |

**永続化の優先順位**（`js/store.js`）：起動時、ログイン済みならクラウドの内容を最優先で採用
（他端末から見に来るケースを想定）。以後の保存は `localStorage`（即時）／`data/state.json`
（ローカルサーバ経由、300msデバウンス）／クラウド（ログイン中のみ、300msデバウンス）の
3箇所に同時に書く。ログインしなくても今まで通りローカルだけで完結して動く（後方互換）。

**⚠️ 手動設定が必要（着工前に必ず1回だけ行う）**：Supabaseダッシュボードの
`Authentication → URL Configuration`（`/dashboard/project/zahhyzplkpqfkuylupkw/auth/url-configuration`）で、
マジックリンクのリダイレクト先として **`http://127.0.0.1:8971`**（`LifeGame.bat`の既定ポート）を
Site URL または Additional Redirect URLs に追加すること。これをやらないと、メール内のリンクを
踏んでもアプリに戻ってこられない（MCPツールにはこの設定を行う手段が無く、ダッシュボードでの
手動操作が必要）。

**実装メモ・ハマった点**：`const Cloud = (() => {...})()` のようにクラシックスクリプトの
トップレベルで `const` 宣言したものは、`Cloud` という識別子としては他のスクリプトから見えるが
**`window.Cloud` にはならない**（`var`や関数宣言と異なる）。`store.js`側で `if (window.Cloud && ...)`
という形でガードを書いてしまい、常にfalseになってクラウド同期が死んでいるバグを実機テスト
（Playwright + ローカルChromium）で発見・修正した。`typeof Cloud !== 'undefined'` で判定するのが正しい。

**未実装（今後の課題）**：複数端末を同時に開いている間のリアルタイム同期は無し
（ログイン時に1回pullするのみ）。Supabase Realtimeで実現できるが今回はスコープ外。
